# Audit Notes (generated while implementing apkxs-v3.md)

This project was written without access to an Android SDK, Gradle, or the
network, so nothing here has actually been compiled. The GitHub Actions
workflow (`.github/workflows/build.yml`) is the first real compile check —
expect to need a few follow-up fixes after the first run. What follows is
what a manual static audit could catch and did catch/fix before handoff.

## Bugs found and fixed during self-review
1. **`RateLimiter` had no `@Inject constructor`** — `HttpClientService`
   depends on it, so Hilt/KSP would have failed with a missing-binding
   error. Fixed, and the interval moved from a constructor default-value
   parameter (which Dagger/Hilt does NOT honor) to a hardcoded field.
2. **`MainViewModel.activeSessionId` was never assigned** — Stop/Export
   would have silently no-opped forever. Added `ScanOrchestratorEvent.Started`
   so the session id reaches the ViewModel.
3. **`CrawlEngine.crawl()`** originally nested a second `callbackFlow` with
   an ad-hoc helper function to re-map events — replaced with a plain
   `.mapNotNull { it.result }`.
4. **`ScanOrchestrator`** originally defined `emitLog` as a member
   extension function on `ProducerScope<ScanOrchestratorEvent>` referenced
   by fully-qualified name, called from inside nested `launch {}` blocks —
   relies on Kotlin's implicit-receiver lookup through nested scopes, which
   works but is fragile/hard to audit. Replaced with an explicitly passed
   `emit: suspend (ScanOrchestratorEvent) -> Unit` lambda, and the
   `ProducerScope` itself is now captured in a named `producerScope` val
   instead of being referenced implicitly for `.close()`.
5. **`collectLatest` → `collect`** in `ScanOrchestrator` — `collectLatest`
   would cancel an in-flight `saveCrawlResult`/event-emit as soon as the
   next crawl result arrived, risking silently lost saves under a fast
   crawl. Every crawl event must be fully processed, so `collect()` is
   correct.
6. **Per-parameter test coroutines had no try/catch** — since
   `ScanOrchestrator` uses a `SupervisorJob`, one parameter's test throwing
   would not kill the scan, but would still surface as an unhandled
   exception. Wrapped in try/catch with an ERROR log instead.
7. **Missing dependencies**: `androidx.appcompat`, `androidx.activity:activity-ktx`,
   and `androidx.lifecycle:lifecycle-runtime-ktx` are used by the UI layer
   (`AppCompatActivity`, `AlertDialog`, `by viewModels()`,
   `lifecycleScope`/`repeatOnLifecycle`) but were **not** in §0.4's original
   dependency list. Added to `gradle/libs.versions.toml` — without them the
   project cannot compile at all. Flagged as a deviation from the spec's
   closed dependency list rather than silently added.
8. **Theme mismatch**: `themes.xml` originally used a plain
   `android:Theme.Material.NoActionBar` parent (since AppCompat wasn't in
   the dependency list yet). Once `AppCompatActivity` was introduced, this
   would crash at runtime (`InflateException`). Switched the theme parent
   to `Theme.AppCompat.NoActionBar`.
9. **No Gradle Wrapper committed** — generating a real
   `gradle-wrapper.jar` needs either a Gradle install or network access,
   neither available here. The workflow installs Gradle directly via
   `gradle/actions/setup-gradle` instead of relying on `./gradlew`. See the
   note at the top of `build.yml` for how to switch back to a committed
   wrapper later.
10. Removed stale `.gitkeep` placeholder files from every package
    directory that now has real source files.

## Automated cross-checks run (all passed)
- No duplicate top-level class/object/interface declarations across the
  whole source tree.
- Every file's `package` statement matches its folder path.
- Every internal `import com.example.xssscanner.*` resolves to an actual
  declaration somewhere in the tree (the only two "unresolved" hits were
  `R` — generated by AGP at build time — and Kotlin extension functions
  `toDomain()`/`toEntity()`, which the grep pattern used doesn't recognize
  but which do exist).
- Every `R.id.*`, `R.string.*`, `R.layout.*`, `R.color.*` reference in
  Kotlin code has a matching declaration in the corresponding XML resource
  file.
- Every `@Inject constructor(...)` parameter list was reviewed; all
  non-trivial parameter types are either other `@Inject`-constructed
  classes, domain interfaces bound via `@Binds` in `RepositoryModule`, or
  provided via `@Provides` in `HttpClientModule`/`DatabaseModule`, or
  `@ApplicationContext Context`.

## Known ambiguities deliberately left as `TODO: needs confirmation` in code
(not bugs — genuine spec gaps/conflicts, each resolved with the simplest
safe interpretation per the Ambiguity Protocol, and called out rather than
silently guessed):
- `ScanOrchestratorEvent` type had to be invented (§8.3 references it, §8's
  model list doesn't declare it).
- `ExportResultsUseCase` returns `List<String>` (URI strings) instead of
  the literally-specified `List<Uri>`, since domain cannot import
  `android.net.Uri`.
- `StartScanUseCase`/`ConfirmExecutionUseCase` depend on concrete
  `scanner`/`webview` classes rather than a domain-level port interface,
  because `domain/repository`'s file list is declared closed at exactly 3
  files.
- `DiscoverParametersUseCase`/`AnalyzeDomXssUseCase` can't re-derive raw
  HTML/JS bodies from the domain `CrawlResult` model (no body field) — the
  real parameter/JS extraction happens inside `CrawlEngine` while the body
  is in hand; these use cases are thinner than their names imply.
- `DomSourceSinkAnalyzer` only does same-line source→sink matching, not
  cross-line/variable-traced taint tracking (§4.5's optional extension).
- `RiskScorer`'s 0-100 formula is invented (§4 doesn't specify one).
- `ExportRepository` writes via `MediaStore.Downloads` / app external files
  dir rather than launching an interactive SAF picker, since SAF's
  `ACTION_CREATE_DOCUMENT` needs an `Activity`/`ActivityResultLauncher`,
  which a plain repository class doesn't have.
- `HiddenWebViewManager`'s `WebViewCompat.addWebMessageListener` wiring is
  marked `TODO(verify-api)` — a real but less-common `androidx.webkit`
  surface that needs the actual compiler/API docs to finalize the callback
  signature.

Search the source tree for `TODO:` and `TODO(verify-` to find every one of
these in context.

## What to do if the GitHub Actions build still fails
Most likely failure points, roughly in order of probability:
1. Version mismatches in `gradle/libs.versions.toml` (every entry is
   marked `TODO(verify-version)` — none were checked against a live Maven
   repository).
2. The `androidx.webkit` `WebMessageListener` wiring in
   `HiddenWebViewManager`/`ExecutionConfirmationBridge` (marked
   `TODO(verify-api)`) — this is the single riskiest API surface in the
   project.
3. Room's KSP annotation processing (schema export path, entity
   validation) — not independently verifiable without actually running KSP.
